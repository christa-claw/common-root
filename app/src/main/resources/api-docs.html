Common Root? — API v1

Read-only access to the corpus: editions, their contents, passages, and a way to prove a quote came from here. Base URL /api/v1. Everything is JSON unless you ask for XML.

Start here: following a token

Every edition is identified by a short token — its abbreviation, lowercased: kjv, web, q-ar, buk-en. Tokens are the same permanent addresses the site's reader links use, so they never change. Wherever a response says "text": "web", that token is the handle for everything else:

You haveCallYou get
a tokenGET /texts/webthe edition record — full name, type (bible / quran / hadith), language, direction, year, licence, whether it can be downloaded
a tokenGET /texts/web/booksits table of contents — every book (surah, hadith book) with its code and the chapter numbers that actually exist
a token + a referenceGET /texts/web/JHN.3.16the verse, span, or chapter, with an attestation
nothing yetGET /textsevery edition, so you can find a token

The pattern is always token → contents → reference. A reference you see in one response can be pasted into the next URL as is.

Keys

Every call except /health and this page needs an API key. Keys are free: create one on your account page. Send it as a Bearer token — and only there:

curl -H "Authorization: Bearer crk_…" https://common-root.org/api/v1/texts/kjv/JHN.3.16

A key in the query string is refused with 401 even if it is valid, because query strings land in access logs and Referer headers; if you have done that, treat the key as leaked and rotate it. You can hold up to five live keys, so rotation is create-new, move traffic, revoke-old. Keys are stored hashed; the plaintext is shown once, at creation.

A key raises your allowance; it never changes what you are entitled to. Licensed editions are not served by the API whatever key you hold.

To try everything on this page without writing code, import the Postman collection (25 requests with assertions, from health to a tampered-bundle verify), set its apiKey variable to your key, and run it. The same file lives in the source repository.

Editions

GET /texts

All editions. Each entry:

{ "id": "bible-web", "token": "web", "abbreviation": "WEB",
  "translation": "World English Bible", "type": "bible", "language": "en",
  "direction": "ltr", "year": "2000", "license": "Public Domain", "downloadable": true }

downloadable is computed by the same licence check that gates the download, so the list never advertises what the gate then refuses.

GET /texts/{token}

One edition, the same shape. The document id is also accepted in place of the token.

GET /texts/{token}/books

{ "text": "kjv", "type": "bible", "count": 80,
  "books": [ { "code": "GEN", "name": "Genesis", "chapters": [1, 2, …, 50] }, … ] }

For a Qur'an the books are the surahs — code is the surah number and nativeName carries the Arabic name; for a hadith collection they are its books. Only chapters that exist are listed: an edition that prints selections is described as it is, not as its canon would suggest.

References

A reference names a passage independently of any edition, in the site's link format:

FormExampleMeaning
BOOK.chapterJHN.3a whole chapter
BOOK.chapter.verseJHN.3.16one verse
BOOK.chapter.verse-versePHP.4.10-13a span within one chapter
Q.surah.ayahQ.2.255Qur'an — surah and ayah; there is no middle level

Book codes are USFM (GEN, 1JN, PHP); /texts/{token}/books lists the ones an edition has. Codes are case-insensitive. A span that crosses a chapter boundary is refused (400) rather than guessed at.

Passages

GET /texts/{token}/{ref}

{ "text": "kjv", "direction": "ltr", "ref": "JHN.3.16",
  "book": { "code": "JHN", "name": "John" }, "chapter": 3,
  "verses": [ { "number": 16, "text": "For God so loved the world, …" } ],
  "attestation": { "alg": "HMAC-SHA256", "kid": "k1", "canon": "v1", "corpus": "…",
                   "minted": "2026-09-06T14:02:11Z", "app": "0.8.0", "tag": "…" } }

direction is stated in every JSON response because plain text cannot carry it. Verse text is the reader's display text: paragraph marks, section marks and stray footnotes removed. Unknown edition or passage: 404.

GET /passages?refs=…

Scattered verses, across books and across editions, in one call. Each reference may carry its own edition as a prefix; src supplies editions for the ones that don't, and may itself be a list, in which case an unprefixed reference is fetched from every edition in it:

GET /passages?src=kjv&refs=JHN.1.1,ROM.9.5,PSA.23.1-6
GET /passages?refs=kjv:1JN.5.7,web:1JN.5.7,vul:1JN.5.7,tr:1JN.5.7
GET /passages?src=kjv,web&refs=GEN.1.1,GEN.1.2
{ "passages": [
    { "text": "kjv", "direction": "ltr", "ref": "1JN.5.7", "book": {…}, "chapter": 5,
      "verses": [ … ], "found": true },
    { "text": "web", … } ],
  "attestation": { … } }

Passages come back in the order asked, at most 20 per call. A passage that does not exist in its edition is returned with "found": false and no verses rather than failing the whole call; a reference that cannot be parsed fails the whole call, and nothing is served. The single attestation covers every passage found, in that order — a comparison of one verse across four translations is one provable object.

Formats

?format=json (default) or ?format=xml; the query parameter wins, otherwise an Accept: application/xml header is honoured. XML is the corpus's own <chapter> element under http://religioustext.org/schema/1.0 — a valid subtree of religious-text.xsd, the same bytes you would cut out of the bulk download, with this site's reading-order attributes removed. It is available for single passages only; /passages and /texts are JSON. The attestation rides inside the document as a processing instruction before the element — <?common-root-attestation alg="…" kid="…" canon="…" corpus="…" minted="…" app="…" tag="…"?> — so a saved file is self-validating; validators ignore it and the element stays a pure schema subtree. Plain text answers 501 until the display modes ship.

Attestation

Every passage response carries a tag that lets anyone later confirm the text came from here, unmodified, for a given corpus version. JSON responses carry it as attestation; every response also carries it as a header:

X-CommonRoot-Attestation: alg=HMAC-SHA256; kid=k1; canon=v1; corpus=…; minted=2026-09-06T14:02:11Z; app=0.8.0; tag=…

The tag is an HMAC-SHA256, under a secret held by this site, over a canonical form — never over the response bytes, so re-serialising, reformatting or converting between JSON and XML cannot invalidate it. Canonical form v1 is UTF-8, lines joined by \n, no trailing newline:

canon:v1
corpus:{corpus label from the attestation}
minted:{minted, from the attestation — ISO-8601 UTC, whole seconds}
app:{app, from the attestation}
text:{edition token}
ref:{reference as returned}
{verse number}<TAB>{verse text}        one line per verse, in order
text:{next edition}                     scattered passages: repeat per passage, in served order
ref:{next reference}
…

Verse text in the canonical form is the display text exactly as the JSON returns it, Unicode-normalised to NFC. If you hold XML, apply the same cleaning (remove ¶ and §, drop an appended footnote of the form 1.4 …, collapse whitespace) before verifying. The kid names the signing key so keys can rotate without orphaning old tags; corpus names the corpus version, so a tag from a past publish still verifies. minted and app are signed too: a valid tag is a timestamp — this text was served by this site, at that moment, from that corpus, by that build — and because they are part of the signed form, the same passage fetched twice carries two different tags. Send the attestation object back exactly as received. Every response is self-validating: JSON carries the attestation in the body, XML in the processing instruction, so a saved file needs nothing but this page to be checked.

Honest limit: the tag is data, not protection. Anyone can remove or alter it. Its value is that if it verifies, the text is ours, unmodified, for that corpus version. A missing tag proves nothing either way.

Verify

POST /verify

Send back what you hold — one passage, or a bundle exactly as served:

{ "text": "kjv", "ref": "JHN.3.16", "attestation": { … },
  "verses": [ { "number": 16, "text": "For God so loved the world, …" } ] }

{ "attestation": { … },
  "passages": [ { "text": "kjv", "ref": "1JN.5.7", "verses": [ … ] },
                { "text": "web", "ref": "1JN.5.7", "verses": [ … ] } ] }

Response: { "valid": true, "attests": "Served by common-root.org on 2026-09-06T14:02:11Z (build 0.8.0): kjv 1JN.5.7; web 1JN.5.7 — corpus …, unmodified.", "minted": "…", "app": "…", "corpus": "current" } — or exactly { "valid": false }, with no reason, whatever went wrong. corpus is current when a fresh fetch would return this same text, superseded when the bundle is authentic but came from an earlier publish, so today's text may differ; validity is unaffected either way. Bodies are capped at 400 verses / 64 KB.

Quotas

Each key has two monthly allowances (calendar month, UTC, reset on the 1st): requests for API calls and bytes for downloads. They are sized so that pulling the whole public-domain corpus once never touches the meter. Every metered response says where you stand:

X-RateLimit-Limit: 20000
X-RateLimit-Remaining: 19987
X-RateLimit-Reset: 1790812800        epoch seconds

Past the allowance, or past 60 requests in a minute, you get 429 with a Retry-After header. Please honour it: retrying in a loop is exactly the load the quota exists to prevent. Requests that fail authentication do not count.

Errors

Every error is JSON, whatever format you asked for:

{ "status": 404, "error": "unknown_source",
  "message": "No edition 'nope'. See /api/v1/texts for tokens.",
  "docs": "https://common-root.org/api/docs#texts" }
StatuserrorWhen
400bad_ref, bad_format, too_many_refs, missing_sourcethe request cannot be honoured as written; nothing partial is served
401missing_key, invalid_key, key_in_query_stringno usable key in the Authorization header
403not_redistributablea licensed edition, whatever key is presented
404unknown_source, no_such_passageno such edition, or the reference is not in it
429quota_exceededallowance or burst limit; see Retry-After
501not_implementedplain-text format, for now

Switch on error, never on message: the slug is stable, the sentence is not.

Health

GET /health needs no key and counts nothing: 200 {"status":"ok"} or 503 {"status":"degraded"} with a per-subsystem breakdown. Point your monitor at it.
